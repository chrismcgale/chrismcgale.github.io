03 / HARDWARE · CUSTOM FLIGHT CONTROLLER · ROUTED, PRE-FAB

Rook

A flight controller of my own design: a 4-layer STM32H743 board for a 7-inch 6S quad, laid out pin-for-pin compatible with Betaflight and ArduPilot so both stacks run on it nearly for free. The whole schematic is generated from code; the board is routed and DRC-clean, waiting on a fab order. Named for the corvid: a rook, the bird that builds and remembers.

1.Why build the flight controller

Every other flying project here has run on someone else's flight controller. Rook is the one I designed myself, from the power tree up. The constraint that shapes the whole board: it is laid out pin-for-pin against the ArduPilot MatekH743 hwdef. Cloning that pin map means the board inherits working Betaflight and ArduPilot targets almost for free, so I can bring up custom firmware against two golden references instead of debugging a board and an estimator at the same time.

This one is deliberately hand-built, not automated. The split I set for myself: the mechanical and generative infrastructure (layer stackup, board outline, net classes, the schematic generator, fab tooling) is scripted and repeatable; the parts that actually teach board design (footprint verification, component placement, routing, the ground and power pours, and the dozen judgment calls the datasheets don't settle) are done by hand. The pin map is the fixed contract; everything else is where the learning is.

2.The board

It is a 36×36 mm four-layer stack on a standard 30.5×30.5 M3 mounting pattern, so it drops onto an off-the-shelf 30.5 ESC. The layer intent is fixed: L1 signal · L2 solid ground plane · L3 power · L4 signal. The interior ground plane is not optional here: the ICM-42688-P needs a quiet ground reference while DShot motor outputs and a switching BEC share the same small board. Fab target is JLCPCB 4-layer ENIG, chosen for the flat pads the 0.5 mm-pitch LQFP-100 and the LGA gyro want.

3.The 6S power tree

6S is where cheap flight controllers die: an inductive spike off a 25 V pack on a hot-plug easily overshoots past 50 V. Rook's input stage is built for it and is the one robustness item I kept even on a personal board:

  • Reverse-polarity P-FET (Si7461DP, 12 V gate clamp) plus an SMAJ33A TVS on the raw battery node. A backwards battery does nothing; the worst hot-plug ring clamps below 53 V, under the 60 V rating of the FET and buck, with margin.
  • 5 V from a TPS54360B 60 V / 3.5 A buck (10 µH, SS56 catch diode): a BEC rated well above the 6S spike envelope, not a 24-32 V part that a spike would kill.
  • 3.3 V for the MCU from an AMS1117 LDO off the 5 V rail, kept separate from the gyro's supply.
  • 3.3 V for the gyro from its own dedicated low-noise TPS7A2033 LDO powering the IMU and nothing else: the gyro's noise floor is a PSRR problem, so it gets its own clean rail and tight decoupling, placed on the opposite side of the board from the power stage and connectors.

4.Schematic as code

The schematic is not drawn by hand: it is generated. A Python script (gen.py) is the source of truth. It emits the KiCad schematic deterministically, each pin fanned out to a named global label, nets joined by name, power nets flagged. The MCU is keyed by pin name against the hwdef map, never hand-numbered, so a transcription slip can't silently reassign a pin. Re-running it is idempotent: a no-op regeneration produces a zero-line git diff, which makes the schematic a real review surface instead of an opaque binary.

The generated core (MCU pin map, gyro / baro / gyro-LDO, USB ESD and USB-C, and the per-subsystem support passives) lands at zero ERC errors. The board that comes out of it is 89 components across 109 nets, routed on four layers and DRC-clean with full schematic parity (0 violations, 0 unconnected, 0 parity issues on the current spin).

5.Invariants the checklist can't catch

A lot of what makes a flight controller work (or brick) is invisible to DRC. The design carries a short list of non-negotiables, each with a reason a rule check would miss:

  • RC input stays on USART6 (PC6/PC7), deliberately clear of the H74x DFU-bootloader UART pins, so a powered receiver or GPS can't hijack the board into the bootloader.
  • VCAP1 + VCAP2: two 2.2 µF low-ESR caps tied together for the H743's internal LDO. Leave them off and the chip simply won't boot: a failure no schematic rule flags.
  • ICM-42688-P RESV pins: some are datasheet "connect to GND", not "no-connect". A floating reserved pin is a flaky-or-bricked gyro that DRC will happily pass.
  • SPI1 MOSI is on PD7, not a PA/PB pin: a non-obvious assignment straight out of the hwdef, easy to "correct" and break.
  • microSD logging on SDMMC1 (not SPI flash): the ArduPilot-native path, brought out on a real 4-bit bus.

6.Status & what's next

Honest status: the schematic and layout are frozen, the board is fully routed, and it passes DRC with schematic parity. It has not been ordered, populated, or flown. The near-term path is a footprint verification pass against every datasheet, then a first fab and assembly run, bring-up over SWD and USB DFU, and a Betaflight target as the first firmware milestone before any of my own control code goes near it. Phase two is a separate board: a DIY AM32 4-in-1 ESC to fly underneath it.
